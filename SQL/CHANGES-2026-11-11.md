# SQL Deployment Pipeline – Change Summary (11 Nov 2026)

## Overview

These changes cover four problems in the feature-based SQL deployment pipeline:

| # | Problem | Fix |
|---|---|---|
| 1 | **Excluding a client didn't cover group entries.** `-ExcludedClients "Client003"` still deployed Client003's database when a checklist row targeted a group entry such as `WorkflowSecondaryServer`. | Each server in the config now has a `clientId`. Excluding a `clientId` skips that client's databases everywhere, including inside group entries. |
| 2 | **`Deploy-FeatureBasedSQL.ps1` was broken.** A bad merge had moved the main block into a function. The script deployed nothing and reported no error. It also didn't accept `-ClientResilienceMode`, which the pipeline passes. | The run logic was rebuilt. The SQL execution, validation and rollback functions are unchanged. |
| 3 | **No defined order when a client fails.** `ContinueOnClientFailure` had no clear rules for ordering or for what happens after a failure. | Order is now Feature_Order → Client → Script_Order. A failure affects only the database it happened on. |
| 4 | **The report didn't show what happened per client.** | The report now has a per-client outcome, a feature summary in run order, and the reasons scripts were skipped. |

Files changed:

| File | Type of change |
|---|---|
| `Environments/qa/qa-config.json` | New `clientId` on every server |
| `Environments/dev/dev-config.json` | New `clientId` on every server |
| `Parse_FeatureChecklist.ps1` | Exclusion by `clientId`, new `-ExcludeExceptions` parameter |
| `Deploy-FeatureBasedSQL.ps1` | Run logic rebuilt; ClientResilienceMode implemented |
| `Publish-DeploymentResults.ps1` | Report improvements |
| `azure-pipelines.yml` | New `Exclude_Exceptions` parameter, fix to the final failure check |

**Contents:** 1. Config files · 2. Parse script · 3. Deploy script · 4. Publish script · 5. Pipeline YAML · **6. Step-by-step guides** · 7. Testing · 8. Open points

## 1. Environment config files – `clientId`

Every entry in `servers[]` now has a `clientId`. Group entries such as `WorkflowPrimaryServer` and `WorkflowSecondaryServer` use the `clientId` of the client whose database they point at.

```json
{
    "clientName": "WorkflowSecondaryServer",
    "applicationName": "workflow",
    "servers": [
        { "serverName": "qa-server2", "clientId": "C003", "connectionStringVar": "qa-client003-connstr", "databases": ["QA_Client3DB_001"] },
        { "serverName": "qa-server2", "clientId": "C004", "connectionStringVar": "qa-client004-connstr", "databases": ["QA_Client4DB_001"] }
    ]
}
```

Current IDs (the same in QA and Dev):

| clientId | Client | Also reached through |
|---|---|---|
| C001 | Client001 | WorkflowPrimaryServer |
| C002 | Client002 (application2 and application6) | – |
| C003 | Client003 | WorkflowSecondaryServer |
| C004 | Client004 | WorkflowSecondaryServer |

**Rules when you add a client:**
- Give every server entry a `clientId`, written as a string (for example `"C005"`).
- A `clientId` must never be the same as any `clientName`.
- A server without a `clientId` can only be excluded by `clientName`. The parse script prints a warning when it finds one.

## 2. `Parse_FeatureChecklist.ps1` – client exclusion

### How `-ExcludedClients` works now

Each comma-separated value can be either kind:

| Value | Effect |
|---|---|
| A **clientId** (for example `C003`) | Every database tagged with that ID is skipped, including databases reached through group entries |
| A **clientName** (for example `Client003` or `WorkflowSecondaryServer`) | Only that config entry is skipped, as before. Other entries pointing at the same databases are **not** affected. |

> **To skip a client everywhere, exclude its `clientId`, not its name.**

### New parameter: `-ExcludeExceptions`

This is a comma-separated list of clientIds to keep even when `-ExcludedClients` covers them. An exception always wins over an exclusion.

| Pipeline input | Result |
|---|---|
| `Excluded_Clients = C003` | Client003's database is skipped, both directly and through WorkflowSecondaryServer |
| `Excluded_Clients = WorkflowSecondaryServer` | The group entry is skipped. Client003 and Client004 still deploy through their own entries. |
| `Excluded_Clients = WorkflowSecondaryServer`, `Exclude_Exceptions = C004` | Everything in the group is skipped except C004's database |

### Checks on the values you pass
- A warning appears when an excluded value matches no `clientName` and no `clientId`, so a typo doesn't go unnoticed.
- A note appears when a value is excluded by name but its databases are still reached through another entry.
- A warning appears when an exception value isn't a known `clientId`.

### Output changes
- **`skipped_rows.csv`:** rows are now written with proper columns: `SQL_Path, Client_Name, Client_Id, Server_Name, Database_Name, Reason`. Before, they were hashtables, which `Export-Csv` writes as unreadable columns.
- **`summary_report.json`:** now includes `ExcludeExceptions`.

## 3. `Deploy-FeatureBasedSQL.ps1` – run order and client resilience

### Fixes to the broken script
- **Main block restored:** reading the execution plan, filtering, running the features and reporting are back at the top level of the script.
- **`-ClientResilienceMode` added:** values are `StopOnFirstClientFailure` (the default) and `ContinueOnClientFailure`.
- **`Write-Checkpoint` calls removed:** the function was never defined.
- **`-FeatureFilter`** now accepts a comma-separated list.
- **Execution plan location:** `execution_plan.csv` is looked for in the artifacts directory first, then in the working directory. The pipeline downloads the plan to the working directory.
- **Rollback result bug fixed:** after an `AtomicFeature` rollback, the rollback function's return value leaked into the feature result. A failed feature could then be treated as successful.

### Run order (both modes)

1. **Features:** ascending `Feature_Order`. Ties are broken by application name, then feature name.
2. **Clients within a feature:** one database at a time, ordered by `Client_Name`, then server, then database.
3. **Scripts within a client:** all scripts for that database run in ascending `Script_Order` before the next client starts.

### `ContinueOnClientFailure` behaviour

Failures are tracked **per database** (server + database), not per `Client_Name`. A failing database inside a group entry therefore doesn't block the group's other databases.

| Situation | Behaviour |
|---|---|
| A script fails for a database | That database's remaining scripts in the feature are **Skipped**. Other clients continue. |
| A feature has failures | The next feature still starts |
| A database failed in an earlier feature | All its scripts in later features are **Skipped** (reason: *failed in earlier feature X*) |
| `RollbackStrategy = Progressive` | Completed scripts stay applied |
| `RollbackStrategy = AtomicFeature` | Only the failed database's successful scripts **in that feature** are rolled back |
| `RollbackStrategy = CascadingApplication` | Only the failed database's successful scripts **across the whole application** are rolled back, latest feature first |

Other clients are never rolled back in this mode.

**Example:** scripts 1–3 for Client001–003, where Client001 fails script 1:

| Client | Script 1 | Script 2 | Script 3 |
|---|---|---|---|
| Client001 | Failed | Skipped | Skipped |
| Client002 | Success | Success | Success |
| Client003 | Success | Success | Success |

### `StopOnFirstClientFailure` behaviour (unchanged)
- The first failure stops the current feature and applies `RollbackStrategy`.
- **AtomicFeature** rolls back the feature for all clients.
- **CascadingApplication** rolls back the whole application and stops the deployment.
- With **Progressive** or **AtomicFeature**, the deployment continues with the next feature. This is how the script behaved before.

### Output
- **`executionsql-results-<BuildId>.csv` and the console table** are now in run order: Feature → Client → Script_Order.
- **Every skipped row records its reason** in `Error_Message`.
- **The failed-features list** shows which databases failed, and which were skipped because of an earlier failure.

## 4. `Publish-DeploymentResults.ps1` – report improvements

| Change | Details |
|---|---|
| **Client / Database Summary** | One row per database, with an overall **Outcome** (*Deployed*, *Failed*, *Failed – partially deployed*, *Failed – rolled back*, *Rolled back*, *Not deployed (skipped)*) and its **First Failure** (feature / script) |
| **Feature Summary (run order)** | Ordered by `Feature_Order`, with outcome, counts and failed clients. This was already calculated but was only written to the JSON. |
| **Skipped Scripts by reason** | Groups skipped rows into *failed in an earlier feature*, *earlier script failed in the same feature* and *deployment stopped*, with the affected clients |
| **Application Summary** | New Rolled Back and Skipped columns |
| **Execution Details** | Shows feature and script order numbers |
| **Summary tiles** | New *Clients* count. "Rolled Back (feature)" renamed to "Rolled Back", because rollback can now apply to a single database. |
| **Empty results file** | Logs a warning and sets `DeploymentStatus=Unknown`, instead of finishing silently |

The new sections appear in the HTML report, the console output and `deployment-analysis.json`.

---

## 5. `azure-pipelines.yml`

- **New parameter `Exclude_Exceptions`** (optional, comma-separated clientIds), passed to the parse script as `-ExcludeExceptions`.
- **`Excluded_Clients` display name** now says it accepts clientIds or clientNames.
- **Final failure check fixed:** "Fail Pipeline If Deployment Failed" read `$(deploymentSuccess)`. That never resolves, so the step could never fail. It now reads `$(deployStep.DeploymentSuccess)`, and the typos in its error message are fixed.

## 6. Step-by-step guides

### 6.1 Rolling out these changes

1. **Copy the changed files to where the pipeline reads them.** The pipeline runs the scripts from `Scripts/` (the deploy and publish steps use `scripts/`). Copy these files into that folder in the repository:
   - `Parse_FeatureChecklist.ps1`
   - `Deploy-FeatureBasedSQL.ps1`
   - `Publish-DeploymentResults.ps1`
2. **Copy the updated config files** to `Environments/qa/qa-config.json` and `Environments/dev/dev-config.json`.
3. **Check that every server entry has a `clientId`.** Open each config file; every object inside `servers[]` must have a `"clientId"` line.
4. **Commit `azure-pipelines.yml`.** It contains the new `Exclude_Exceptions` parameter and the fixed failure check.
5. **Check the scripts parse.** In Windows PowerShell 5.1, run this from the repository root:
   ```powershell
   foreach ($f in Get-ChildItem .\Scripts\*.ps1) {
       $errs = $null
       $null = [System.Management.Automation.Language.Parser]::ParseFile($f.FullName, [ref]$null, [ref]$errs)
       "{0,-35} parse errors: {1}" -f $f.Name, @($errs).Count
   }
   ```
   Every file must show `parse errors: 0`.
6. **Commit and push** to a branch, and raise a pull request for review.
7. **Run in dev first** with a dry run (6.2), then a real run (6.3). Move on to QA only after dev succeeds.

### 6.2 Doing a dry run (checks the plan, deploys nothing)

1. In Azure DevOps, open the pipeline and click **Run pipeline**.
2. Fill in the parameters:

   | Parameter | Value |
   |---|---|
   | Release_Version | The release you are deploying, e.g. `1.0` |
   | Environment | `dev` |
   | Feature Filter | `all`, or a comma-separated list such as `FeatureA,FeatureB` |
   | Excluded Clients | Leave empty, or see 6.4 |
   | Exclude Exceptions | Leave empty, or see 6.4 |
   | Dry Run | **checked (true)** |

3. Click **Run**. Only the **Parse Feature-Based Release Checklist** stage runs.
4. Open the log of the **Parse Feature-Based Release Checklist** step and check:
   - `Excluded clients :` lists what you entered.
   - Each `[EXCLUDED] ...` line names the server/database you expected to skip.
   - There is **no** `WARNING: Excluded value '...' does not match any clientName or clientId` line. If there is, you have a typo.
   - Read any `Note: '...' skips only the '...' config entry` line. It means a client you excluded by name is still reached through another entry; use its clientId if you want to skip it everywhere.
   - `Sample Execution Plan (first 10 rows)` and `Skipped Rows` look right.
5. The dry run only prints the first 10 plan rows and doesn't publish `execution_plan.csv`. To review the full plan, do a real run and download the **ExecutionPlan** artifact at the manual approval step (6.3, step 4).

### 6.3 Doing a real deployment

1. Click **Run pipeline** and fill in the same parameters as the dry run, with these changes:

   | Parameter | Value |
   |---|---|
   | Client Resilience Mode | `ContinueOnClientFailure` keeps other clients deploying when one fails. `StopOnFirstClientFailure` stops the feature at the first failure. |
   | Rollback Strategy | See the table in 6.5 |
   | Dry Run | **unchecked (false)** |

2. Click **Run**. The stages run in this order: **Parse** → **Validate SQL Scripts** → **Manual Approval** → **Deploy**.
3. **Parse stage:** check the log as in 6.2.
4. **Manual Approval:**
   1. Open the run summary and download the **ExecutionPlan** artifact.
   2. Open `execution_plan.csv` and check the rows (one per script per database). Make sure no excluded database appears.
   3. Open `skipped_rows.csv` to see what was excluded and why (`Reason` column).
   4. Click **Resume** to deploy, or **Reject** to stop.
5. **Deploy stage:** the log of **Execute Feature-Based SQL Deployment Script** shows:
   - `Feature execution order:` lists the features in the order they will run.
   - For each feature, one `Target: client '...' (server.database)` block per database, with each script in order.
   - Failures are marked `[-]`, and skipped scripts `[SKIPPED]`, with the reason.
6. When the run finishes, read the report (6.7).

### 6.4 Excluding clients

**Skip one client everywhere, including inside group entries:**
1. Find the client's `clientId` in the environment config file (see the table in section 1). For example, Client003 = `C003`.
2. Set **Excluded Clients** = `C003`.
3. Leave **Exclude Exceptions** empty.

**Skip several clients:** list them separated by commas, e.g. `C003,C004`.

**Skip a group entry, but keep one client inside it:**
1. Set **Excluded Clients** to the group's `clientName`, e.g. `WorkflowSecondaryServer`.
2. Set **Exclude Exceptions** to the clientId to keep, e.g. `C004`.
3. Result: the group's C003 database is skipped and its C004 database still deploys. Client003's and Client004's own entries are not affected.

**Skip only one config entry**, for example one client's application6 entry but not application2: you can't do this with a clientId, because both entries share `C002`. Excluding `Client002` by name skips **both** Client002 entries. To exclude just one entry, use **Application Filter** or the checklist instead.

Always do a dry run (6.2) after changing exclusions and check the `[EXCLUDED]` lines.

### 6.5 Choosing ClientResilienceMode and RollbackStrategy

| You want… | Client Resilience Mode | Rollback Strategy |
|---|---|---|
| One failing client doesn't block the others; keep whatever completed | ContinueOnClientFailure | Progressive |
| One failing client doesn't block the others; undo that client's partial feature | ContinueOnClientFailure | AtomicFeature |
| One failing client doesn't block the others; undo everything that client got in this application | ContinueOnClientFailure | CascadingApplication |
| Stop a feature at the first failure and keep completed scripts | StopOnFirstClientFailure | Progressive |
| Stop a feature at the first failure and undo it for **all** clients | StopOnFirstClientFailure | AtomicFeature |
| Stop at the first failure and undo the whole application for **all** clients | StopOnFirstClientFailure | CascadingApplication |

Rollback only works for scripts that have a `Rollback_script_path` in the checklist, and the rollback file must exist.

### 6.6 Adding a new client

1. **Choose a new `clientId`**, e.g. `C005`. It must not already be used, and must not equal any `clientName`.
2. **Add an entry** to `Environments/<env>/<env>-config.json` for each application:
   ```json
   {
       "clientName": "Client005",
       "applicationName": "application5",
       "environment": "",
       "servers": [
           {
               "serverName": "qa-server1",
               "clientId": "C005",
               "connectionStringVar": "qa-client005-connstr",
               "databases": [ "QA_Client5DB_001" ]
           }
       ]
   }
   ```
3. **If the client is part of a group entry** (e.g. `WorkflowSecondaryServer`), add a server object to that group's `servers[]` with the **same** `clientId` (`C005`).
4. **Add the connection string** as a secret in the variable group used by the deploy job.
5. **Map the secret** in `azure-pipelines.yml`, in the `env:` block of **Execute Feature-Based SQL Deployment Script**. The left-hand name must match `connectionStringVar` exactly:
   ```yaml
   env:
     qa-client005-connstr: $(qa-client005-connstr)
   ```
6. **Add the client** to the `Client_Name` column of the checklist rows that should deploy to it.
7. **Do a dry run** (6.2). There must be no `Client '...' not found in configuration` warning and no `Some servers ... have no clientId` warning.

### 6.7 Reading the deployment report

1. Open the pipeline run and download the **ExecutionResults** artifact.
2. Open `deployment-report-<BuildId>.html` in a browser.
3. Check the sections in this order:

   | Section | What to look for |
   |---|---|
   | Summary tiles | Overall status, failed, skipped and rolled-back counts |
   | **Client / Database Summary** | The **Outcome** of each database. For anything that isn't *Deployed*, the **First Failure** column shows the feature and script where it went wrong. |
   | **Feature Summary (deployment order)** | Which features had failures, and which clients failed in each |
   | **Skipped Scripts** | Why scripts were skipped. *Failed in an earlier feature* and *Earlier script failed in the same feature* are consequences of a failure, not separate problems. |
   | Execution Details | Every script, in run order, with its error message |
   | Failure Analysis | Failure type and recommended action |

4. **Fix the root cause.** Start from the **First Failure** of each failed database, fix that script or environment problem, and re-run the deployment for those clients only. For example, use **Application Filter** or **Feature Filter**, or exclude the clients that already succeeded.

### 6.8 Troubleshooting

| Message or symptom | Cause | Fix |
|---|---|---|
| `Excluded value 'X' does not match any clientName or clientId` | Typo, or the value is in a different environment's config | Correct the value and check it against the config file |
| `Exception value 'X' does not match any clientId` | Exceptions must be clientIds, not names | Use the clientId, e.g. `C004` |
| `ExcludeExceptions ... ignored because ExcludedClients is empty` | Exceptions only apply to what is excluded | Fill in **Excluded Clients** too |
| A client is still deployed through a group entry | It was excluded by `clientName` | Exclude its `clientId` instead |
| `Some servers ... have no clientId` | A server entry is missing `clientId` | Add `clientId` to that entry (6.6) |
| `Connection string variable '...' not set` | The secret isn't in the variable group or isn't mapped in `env:` | Follow steps 4–5 of 6.6 |
| `execution_plan.csv not found. Searched: ...` | The ExecutionPlan artifact wasn't downloaded | Check that the Parse stage published the artifact and the **Download Execution Plan** step succeeded |
| `No execution plan rows after applying filters` | Application or Feature Filter matches nothing in the plan | Check the spelling; feature names are separated by commas |
| `Client '...' not found in configuration` | A `Client_Name` in the checklist doesn't exist in the config file | Add the client to the config (6.6) or fix the checklist |
| Publish step: `No deployment result files found` | The deploy step failed before writing results | Look at the deploy step log for the first error |

## 8. Open points / follow-ups

1. **Skipping carries across applications.** In `ContinueOnClientFailure`, a database that fails in one application is also skipped for later features of other applications. This can be limited to the same application if needed.
2. **`StopOnFirstClientFailure` doesn't stop the whole run.** It continues with the next feature unless the strategy is `CascadingApplication`. Decide whether it should stop the whole deployment.
3. **Missing results file fails the publish step.** If deployment fails before writing a results file, the publish step exits 1 and adds a second failure to the log. It could log a warning instead.
4. **Script paths in the pipeline.** The pipeline runs the scripts from `Scripts/` (and `scripts/`). Make sure the updated files are committed to that folder.
5. **New clients** must have a `clientId` on every server entry; see section 1.
